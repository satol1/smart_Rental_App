# RentalApp Constitution

## Core Principles

### I. Слоистая архитектура (НЕГОТИЦИРУЕМО)

Роутер → сервис → репозиторий. Роутеры не содержат бизнес-логики и прямых запросов к БД; сервисы не знают про HTTP; репозитории инкапсулируют SQL. Соблюдается принцип единственной ответственности (SRP), DRY: новые сущности создаются только при невозможности переиспользовать существующие централизованные компоненты. Код явный, без «магии». Наследует RULES.md проекта.

### II. Безопасность по умолчанию (НЕГОТИЦИРУЕМО)

- Никаких секретов в коде: ключи, пароли и токены передаются через env и fail-fast валидируются при старте в проде (отсутствие/дефолтное значение = отказ запуска).
- Защита, которая написана, должна быть включена: мёртвый код защиты (валидация в try/except, незарегистрированный middleware) приравнивается к уязвимости.
- Принцип минимальной поверхности: СУБД и внутренние сервисы не публикуются наружу; документация API и отладочные заголовки отключены в проде; каждый эндпоинт осознанно либо публичен, либо защищён ролью.
- Токены: проверка типа (access ≠ refresh), инвалидация при logout, ротация refresh.

### III. Spec-Driven Development

Каждая функциональность начинается со спека (`/speckit.specify`), проходит уточнение (`/speckit.clarify`), план (`/speckit.plan`) и декомпозицию (`/speckit.tasks`) до написания кода. Спек описывает ЧТО и ДЛЯ КОГО, план — КАК. Реализация без спека допускается только для hotfix-патчей безопасности и багфиксов меньше 50 строк.

### IV. Тесты — шлюз слияния

Код не попадает в main без: пройденных тестов (pytest backend, vitest frontend), линтеров (ruff, eslint) и проверки типов (mypy, tsc). Новая функциональность сопровождается тестами; правки безопасности — тестами на атакуемый сценарий. Покрытие фронтенда растёт с каждой фичей (минимум: затронутые компоненты/хуки).

### V. Единообразие интерфейса

- Только design tokens (CSS-переменные из дизайн-системы) — сырые hex-цвета и «магические» отступы в компонентах запрещены.
- Переиспользуемые примитивы ui/ (shadcn/Radix) прежде кастомных реализаций; формы — react-hook-form + zod со схемами в `validationSchemas.ts`; тосты — sonner; иконки — lucide.
- Доступность WCAG 2.1 AA: контраст 4.5:1, видимая фокус-обводка, размеры интерактивных зон ≥44px, `prefers-reduced-motion` уважается всеми анимациями.
- Анимации — через framer-motion по единой шкале длительностей; анимация несёт смысл (переход, фидбек), а не украшение.

### VI. Простота и наблюдаемость

Начинать с простейшего работающего решения (YAGNI). Каждое усложнение (новый сервис, библиотека, слой) обосновывается в плане. Прод-поведение наблюдаемо: структурированные логи, healthcheck каждого контейнера, метрики не торчат наружу без аутентификации.

## Стандарты стека

- **Backend**: Python 3.11+, FastAPI, SQLAlchemy 2 async, Alembic, dependency-injector. Зависимости pinned (`==`) в requirements.txt; тестовые зависимости — только в requirements-test.txt и тестовые образы.
- **Frontend**: React 19, TypeScript strict (сборка блокируется ошибками типов: `tsc -b && vite build`), Vite, Tailwind + shadcn/Radix, TanStack Query, zustand, react-hook-form + zod, framer-motion.
- **API**: изменения контрактов — обратно совместимы либо версионируются (`/api/v1`).
- **БД**: изменения схемы только через Alembic-миграции с рабочим downgrade; одна голова ревизий.
- **Infra**: multistage Dockerfile, non-root USER, HEALTHCHECK, `.dockerignore` в каждом контексте сборки; образы не содержат тестовых зависимостей.

## Процесс разработки

1. `/speckit.specify` → спек фичи в `specs/NNN-name/spec.md`.
2. `/speckit.clarify` (при неоднозначностях) → `/speckit.plan` → план в `specs/NNN-name/plan.md`.
3. `/speckit.tasks` → задачи; реализация по задачам с коммитами.
4. CI обязателен к прохождению; деплой на VPS — по явной инструкции из Docs/DEPLOYMENT.
5. Правки безопасности (принцип II) выполняются вне очереди, кратчайшим патчем, с последующим покрытием тестом.

## Governance

- Конституция главенствует над личными предпочтениями и старыми практиками; при конфликте — решение по конституции.
- Поправки к конституции оформляются коммитом с обоснованием, версией и планом миграции затронутого кода.
- Сложность сверх принципов требует записи в Complexity Tracking плана фичи.
- Рабочие ограничения разработки: см. RULES.md; архитектура — Docs/ARCHITECTURE.md.
