Действующая редакция: **2.0 от 07.09.2026** (модернизирована; предыдущая — см. git history).
Юридически обязательная версия принципов — [Конституция SpecKit](.specify/memory/constitution.md). Этот файл — её рабочая раскладка для промптов и повседневной разработки.

## 1. Системная директива (вставляй в начало сложных промптов)

```text
Ты — мой ассистент по программированию. Проект: веб-приложение аренды фототехники
(FastAPI + React 19 + PostgreSQL, Docker Compose). Ветка работы — feature-ветка, не main.

**Правила, которые ты ОБЯЗАН соблюдать:**

1. АРХИТЕКТУРА: слоистая — роутер → сервис → репозиторий. Роутеры тонкие (без бизнес-логики
   и SQL), сервисы не знают про HTTP, репозитории инкапсулируют запросы к БД.
2. ПРИНЦИПЫ: SOLID (особенно SRP), DRY, чистый код. Новые сущности — только если нельзя
   переиспользовать существующие централизованные компоненты.
3. SPEC-DRIVEN: функциональность начинается со спека (/speckit.specify → clarify → plan →
   tasks → implement). Багфиксы <50 строк и security-hotfix — исключение.
4. БЕЗОПАСНОСТЬ ПО УМОЛЧАНИЮ: никаких секретов в коде (только env, fail-fast в проде);
   защита, которая написана, должна быть включена; каждый эндпоинт осознанно публичный
   или защищённый ролью; СУБД и метрики не наружу.
5. ТЕСТЫ — ШЛЮЗ: новый функционал сопровождается тестами; security-фикс — тестом на
   атакуемый сценарий. Ничего не сливается с красным CI.
6. UI: только design-токены (никаких сырых hex в компонентах); примитивы ui/ прежде
   кастома; формы — react-hook-form + zod; анимации — framer-motion по единой шкале
   (150/200/300ms) с уважением prefers-reduced-motion; доступность WCAG 2.1 AA.
7. НИКАКОЙ МАГИИ: код явный и читаемый; сложность сверх принципов — только с обоснованием
   в плане фичи.
```

## 2. Специфические стандарты (краткая выжимка)

### Backend (Python 3.11 / FastAPI)
- Зависимости: `requirements.txt` — только runtime, всё запинено `==`; тестовое — в `requirements-test.txt`. Образ не содержит тестовых зависимостей.
- Токены: проверка claim `type` (access ≠ refresh), ротация refresh, denylist при logout.
- Лимиты: глобальный rate limit + строгие на auth-эндпоинтах.
- Миграции: только Alembic, авто-ID ревизий, рабочий downgrade, одна голова.
- Прод-режим: `DEBUG=False` → без /docs, без стек-трейсов, детали ошибок не наружу.
- Изменения контрактов API — обратно совместимы или версионируются (`/api/v1`).

### Frontend (React 19 / TypeScript strict / Vite)
- Серверное состояние — TanStack Query; клиентское — zustand (persist — только тема); формы — RHF + zod, схемы централизованы в `src/lib/validationSchemas.ts`.
- Транспорт — только через сервисы `src/core/services/*` (никаких прямых axios в компонентах).
- Страницы — `React.lazy` + `Suspense` со скелетонами; новые страницы добавлять лениво.
- Тексты интерфейса — в словарь i18n (`src/i18n/`), не хардкодить в JSX.
- Тени типов: `any` запрещён в новом коде; сборка = `tsc -b && vite build`.
- Тесты: каждая новая страница/форма/хук — с тестом (vitest); цель — непрерывный рост покрытия.

### Инфраструктура (Docker / CI)
- Образы: multistage, HEALTHCHECK, `.dockerignore` в каждом контексте. Backend — non-root USER; frontend — официальная модель nginx (root-мастер читает TLS-ключи и занимает 80/443, воркеры — непривилегированный nginx).
- Прод-compose: никаких published-портов у БД, никаких bind-mount исходников, healthchecks у всех сервисов.
- CI обязателен: ruff + mypy + pytest (backend), eslint + tsc + vitest + build (frontend).
- Обновление зависимостей — еженедельно через Dependabot, осознанно (security-обновления — сразу).

### Работа с секретами
- `.env` — только локально, в git никогда; прод-секреты — на сервере вне репо.
- Дефолтных значений секретов в коде нет; прод без явных секретов не стартует.
- Утечка секрета (коммит, лог, дамп) = немедленная ротация + чистка истории.

## 3. Шаблоны промптов

### 🐞 Шаблон 1: Исправление бага

```text
[ВСТАВЬ СИСТЕМНУЮ ДИРЕКТИВУ]

**Задача: Исправить баг**

1. Описание проблемы / полный лог ошибки: [...]
2. Контекстные файлы: [@api/... — что связано]
3. План: локализуй причину → план исправления → сохрани в specs/ (если фикс <50 строк,
   план в чате) → после моего одобрения реализуй.
4. Тест: добавь/обнови тест, фиксирующий баг (red → green).
```

### ✨ Шаблон 2: Новая функциональность

```text
[ВСТАВЬ СИСТЕМНУЮ ДИРЕКТИВУ]

**Задача: [название]**

1. Что и зачем (бизнес-языком): [...]
2. Запусти SpecKit-флоу: /speckit.specify "[описание]" → /speckit.clarify → /speckit.plan
   → /speckit.tasks → реализация по задачам.
3. Требования к реализации (если есть конкретика): [...] — они попадут в spec/plan.
```

### 🔐 Шаблон 3: Security-hotfix (вне очереди)

```text
[ВСТАВЬ СИСТЕМНУЮ ДИРЕКТИВУ]

**Задача: Security-hotfix**
1. Уязвимость/находка: [...] (например, из Reports/AUDIT_REPORT_*.md, пункт K-N)
2. Действия: кратчайший патч + тест на атакуемый сценарий + проверка, что защита
   действительно включена (не dead code). Спек не требуется.
3. После фикса: проверить смежные вхождения той же проблемы.
```

### 🧪 Шаблон 4: Тестирование

```text
[ВСТАВЬ СИСТЕМНУЮ ДИРЕКТИВУ]

**Задача: Тесты**
1. Область: [unit / integration / e2e / front]
2. Backend: pytest через .venv или docker compose -f docker-compose.unit-tests.yml ...
3. Frontend: cd rental-app-main && npm run test:run (vitest)
4. Новый тест: сначала red (падает на текущем коде), потом green.
```

## 4. 🐳 Docker — шпаргалка (актуальные команды)

```bash
# Сборка и запуск (современный синтаксис: docker compose, без дефиса)
docker compose up -d --build

# Логи / статус
docker compose ps
docker compose logs -f backend

# Перезапуск одного сервиса
docker compose restart backend

# Полный сброс
docker compose down            # контейнеры и сеть
docker compose down -v         # + тома (ОСТОРОЖНО: удалит данные БД)

# Разовые команды в контейнере (pytest недоступен в прод-образе — только стеки ниже)
docker compose exec db pg_dump -U $POSTGRES_USER $POSTGRES_DB > backup.sql

# Тестовые окружения (отдельные compose в RentalApp_FASTAPI/; изоляция от рабочего стека)
cd RentalApp_FASTAPI
docker compose -f docker-compose.unit-tests.yml up --build --abort-on-container-exit
docker compose -f docker-compose.unit-tests.yml down -v   # после каждого прогона

# Слабый VPS (1 vCPU / 2GB)
docker compose -f docker-compose.limited-resources.yml up -d --build

# Проверка конфигурации без запуска
docker compose -f docker-compose.yml config -q
```

**Правила инфраструктуры:** прод-конфиг — только `docker-compose.yml` (или limited); тестовое — через `-f` профили; ничего не публиковать наружу, кроме 80/443 фронтенда; после любых правок compose — `docker compose config -q`.

## 5. SpecKit-флоу (обязателен для функциональности)

```text
/speckit.specify "описание фичи"   → specs/NNN-name/spec.md      (ЧТО и ДЛЯ КОГО)
/speckit.clarify                    → снятие неоднозначностей
/speckit.plan                       → specs/NNN-name/plan.md      (КАК: стек, фазы)
/speckit.tasks                      → specs/NNN-name/tasks.md     (декомпозиция)
реализация по задачам               → с тестами, чекбоксы закрываются
```

Конституция проекта: `.specify/memory/constitution.md` (главенствует при конфликтах).
Программа `specs/001-platform-modernization/` (аудит → план → задачи) завершена и влита в main (v5.0.3); новые фичи — по новым спекам.
