# План упрощения сложности DI-графа

## 1. Диагностика (что было не так)

### 1.1. God Composition Root
- **Файл:** `RentalApp_FASTAPI/containers.py` (474 строки, ~65 провайдеров)
- Все провайдеры в одном плоском классе, без доменной модульности.
- Инфраструктура (engine, session), репозитории и сервисы — в одном namespace.

### 1.2. Silent overwrites (мёртвый код)
- Dashboard-сервисы (`focus_service`, `kpi_service`, `activity_service`, `equipment_service`, `dashboard_service`) определены дважды: строки 362–366 перезаписываются строками 461–474.
- Первые определения — мёртвый код, который никогда не исполняется.

### 1.3. Temp-провайдеры для циклических зависимостей
- 5 временных провайдеров (`rental_repo_temp`, `rental_query_repo_temp`, `rental_command_repo_temp`, `rental_financial_repo_temp`, `order_validator` без `financial_service`).
- Причина: циклическая зависимость `AvailabilityService → RentalRepository → FinancialService → OrderValidator → AvailabilityService`.

### 1.4. Смешение уровней абстракции
- В одном контейнере: `db_session` (инфраструктура), `user_repo` (репозиторий), `auth_service` (сервис), `equipment_service_api` (API-фасад).

### 1.5. God Service (RentalLifecycleService)
- 11 параметров конструктора — признак нарушения SRP.

### 1.6. Фронтенд: Service Locator вместо DI
- React Context выступает Service Locator, сервисы используют глобальный `api`, нет constructor injection.

## 2. Что сделано (Фаза 1 — Рефакторинг ядра)

Старый монолит заменён на пакет `containers/`:

```
containers/
├── __init__.py          # Container-агрегатор + 78 плоских алиасов
├── constants.py         # Engine, session factories, context var, импорты
├── infrastructure.py    # InfrastructureContainer
├── repositories.py      # RepositoriesContainer
└── services.py          # ServicesContainer (6 фаз инициализации)
```

### Решено:
- ✅ God Container → 3 суб-контейнера + агрегатор
- ✅ Silent overwrites устранены
- ✅ Temp-провайдеры изолированы, циклическая зависимость разбита на 2 фазы
- ✅ Полная обратная совместимость — 0 изменений в API-файлах
- ✅ `Provide[Container.xxx]`, wiring и все импорты работают без изменений

## 3. Что осталось (Фазы 2–5)

### Фаза 2: Устранение циклических зависимостей в domain model
- **Выделить `AvailabilityPolicy`** — stateless-сервис без зависимостей от БД, чтобы разорвать цикл на уровне домена (а не на уровне инициализации контейнера).
- **Внедрить Event-Driven подписку** для cross-domain операций (события `RentalCreated`, `RentalReturned`).
- **Разделить `RentalRepository`** — вынести `financial_service` из репозитория (нарушение Repository Pattern).

### Фаза 3: Упрощение God Services
- Сократить `RentalLifecycleService` до 5±2 параметров через объединение связанных зависимостей в `ServiceContext`.

### Фаза 4: Фронтенд — настоящий DI
- Внедрить `tsyringe` или `inversify`.
- Сервисы должны получать `ApiClient` через конструктор.

### Фаза 5: Метрики и CI
- Тесты: не более 20 провайдеров на суб-контейнер, не более 7 параметров конструктора.
- Статический анализатор циклических зависимостей в CI.

## 4. Резюме: насколько это нужно для работающего проекта?

### Если проект не требует дальнейших разработок и оптимизаций

**Фаза 1 (рефакторинг ядра) — нужна условно.**
- Текущая реализация **работает**. Циклические зависимости разрешены через temp-провайдеры, хоть и ценой читаемости.
- Silent overwrites — это мёртвый код, который не влияет на поведение.
- Если проект заморожен — рефакторинг не имеет практического смысла. Его единственная ценность: снижение когнитивной нагрузки при чтении.
- **Вердикт: не обязательно.** Если бы Фаза 1 уже не была сделана, я бы рекомендовал пропустить.

**Фазы 2–5 — не нужны для работающего проекта.**
- Фаза 2 (устранение циклических зависимостей в domain model) — это архитектурная инъекция, которая требует изменения бизнес-логики. Риск регрессии не оправдан, если проект не развивается.
- Фаза 3 (упрощение God Services) — cosmetic, не влияет на поведение.
- Фаза 4 (фронтенд) — замена Service Locator на DI не даёт выгоды для замороженного проекта.
- Фаза 5 (CI-метрики) — избыточна без активной разработки.

### Если проект будет развиваться

**Фаза 1 — нужна.** Уже сделана.

**Фаза 2 — рекомендуется.** Циклические зависимости между `AvailabilityService`, `RentalRepository` и `FinancialService` будут усугубляться с каждым новым функциональным требованием. Чем раньше разорвать цикл, тем дешевле обойдётся внедрение новых фич.

**Фаза 3 — рекомендуется.** `RentalLifecycleService` с 11+ параметрами — это бомба замедленного действия. Каждый новый разработчик, добавляющий сюда зависимость, не задумываясь увеличивает связность.

**Фаза 4 — опционально.** Фронтенд работает, React Context достаточно производителен. Переход на `tsyringe` оправдан только если фронтенд будет значительно расширяться.

**Фаза 5 — рекомендуется.** Автоматические проверки защищают от деградации архитектуры при командной разработке.

### Итоговая оценка

| Этап | Для замороженного проекта | Для развивающегося проекта |
|------|--------------------------|---------------------------|
| Фаза 1 (рефакторинг ядра) | Не обязательна (сделана) | Обязательна |
| Фаза 2 (разрыв циклических deps) | Не нужна | Рекомендуется |
| Фаза 3 (упрощение God Services) | Не нужна | Рекомендуется |
| Фаза 4 (фронтенд DI) | Не нужна | Опционально |
| Фаза 5 (CI-метрики) | Не нужна | Рекомендуется |

### Главный вывод

**DI-граф — это архитектурный technical debt, который не проявляется в runtime.** Приложение работает и без рефакторинга. Переплачивать за читаемость и поддерживаемость стоит только если проект живёт и развивается. Для замороженного проекта затраты на рефакторинг (даже готовый) не окупаются. Но если вы читаете этот документ — значит, проект ещё не заморожен окончательно, и вложения в архитектуру имеют смысл.
