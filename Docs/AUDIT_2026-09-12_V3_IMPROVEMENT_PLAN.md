# Полный аудит RentalApp №3 и план поэтапного внедрения улучшений

**Дата:** 12.09.2026 · **Ветка:** `feat/rental-design-system-v2` (HEAD `e456c32`) · **Метод:** статический разбор кода + live-проверка работающего стека (прод-контейнеры на машине, БД 213 позиций каталога, 5 резервов, 3 аренды, 1 пользователь-админ).

Аудит третьего цикла: проведён после полного внедрения планов [2026-09-11](AUDIT_2026-09-11_IMPROVEMENT_PLAN.md) и [2026-09-12](AUDIT_2026-09-12_IMPROVEMENT_PLAN.md) (этапы 0–6). Приоритет владельца — жизненный цикл заказа: **резерв → аренда → возврат / частичный возврат / добор / отмена / возврат с долгом / возврат долга**. Эта цепочка разобрана по коду целиком (api/services/order/*, financial/balance/status), плюс live-пробы прод-конфига и публичной витрины в браузере.

> **Важно про метод:** запланированные пять параллельных глубоких проверок (UI/UX, фронт-контракт, инфраструктура) были прерваны исчерпанием недельной квоты токенов — их зоны покрыты выборочно (live-обход витрины, точечные разборы), а не исчерпывающе. Находки ниже — только то, что проверено вручную по коду или живой системой.

---

## 1. Резюме

Прошлые два цикла держатся: анти-овербукинг (advisory-локи + перепроверка при конвертации/продлении/редактировании), Decimal-деньги с `Numeric(12,2)` и `FOR UPDATE` на балансе, post-commit побочные эффекты, защита от двойного возврата и окно отмены «день создания» — подтверждены кодом. TZ `Europe/Astrakhan` в контейнере — live-проверено. nginx отдаёт uploads (200 image/jpeg), не торчит openapi, полный набор security-заголовков.

Новые проблемы — в четырёх зонах:

1. **Прод-конфиг небезопасен** (live-проверено): `DEBUG=true` + `CORS_ALLOW_WILDCARD=true` дают CORS, отражающий любой Origin с `allow-credentials:true`; refresh/CSRF-cookie уходят без `Secure`. Каналы уведомлений (Telegram, email) — плейсхолдеры: менеджер не получает никаких уведомлений.
2. **Цепочка заказов неполна функционально**: частичный возврат и добор позиций к активной аренде не реализованы ни в API, ни в UI; отмена — жёсткое удаление записи без статуса «отменён»; долг (отрицательный баланс) не мешает клиенту набирать новые заказы; сервис автоблокировки должников — мёртвый код без единого вызова.
3. **Витрина замусорена данными синка Bukza**: служебные суффиксы в названиях («(Переменный!!!!)», «-/NEW/- (1)»), категории в списке брендов, «Объединять одинаковые» не работает на реальных данных, изображения зашиты в сборку фронта.
4. **Деньги**: семантика типов операций баланса размывается (возврат при уменьшении стоимости пишется как «кредит за досрочный возврат»), депозит нигде не проводится, «возврат долга» неотличим от обычного пополнения.

Обнаружено **3 критические находки** (все подтверждены live или чтением кода целиком) и ~13 высоких/средних.

## 4. План поэтапного внедрения

Порядок: «сначала закрыть прод-конфиг и утечки процесса, потом достроить цепочку заказов (долги → частичный возврат/добор → история отмен), потом витрина и данные, потом хвосты». Каждый этап — отдельный PR/группа PR с чек-листом приёмки.

### Этап 0 — Хотфиксы прод-конфига (1–2 часа)

| Задача | Что делать | Проверка приёмки |
|--------|-----------|------------------|
| 0.1 **DEBUG и CORS** (К1) | В прод-`.env`: `DEBUG=false`, `CORS_ALLOW_WILDCARD=false`; `CORS_ORIGINS=https://digital30.ru` (+ dev-ориджины только в dev-`.env`). `docker compose up -d backend` | Live-пробы из этого аудита: preflight с чужим Origin — без `access-control-allow-origin`; GET — без `*`; `Set-Cookie` refresh/CSRF содержит `Secure` |
| 0.2 **Уведомления** (К2) | Вписать реальные TELEGRAM_TOKEN/CHAT_ID и YANDEX_EMAIL_SENDER; либо осознанно отключить: флаг в settings + скрыть обещания уведомлений из UI | Создание тестового резерва → сообщение приходит (или фича выключена и не видна) |

### Этап 1 — Долги: контроль и гашение (2–4 дня)

| Задача | Что делать |
|--------|-----------|
| 1.1 **Порог долга при выдаче** | В `validate_user_can_receive_rental` (и на создании резерва админом): проверка `balance >= -max_debt` (настройка в settings, default например 0). Менеджеру — мягкое предупреждение в ответе (или 409 с флагом force, как у выдачи в выходной) |
| 1.2 **Оживить OverdueCheckerService** | Подключить к расписанию: минимально — cron-сервис в compose (обёртка `python -m scripts.run_overdue_check`), в перспективе — ARQ (отложенный хвост). Тест на реальной сессии |
| 1.3 **Тип операции DEBT_REPAYMENT** | Пополнение, которое приводит баланс из отрицательного в ≥0 (или уменьшает долг), помечать `DEBT_REPAYMENT` в `process_user_payment`/`add_transaction`; отчет «должники» на дашборде: список users с balance < 0 |
| 1.4 **UI долга** | В админ-карточках клиента (резервы/аренды/пользователи) — бейдж долга с суммой; при создании аренды должнику — предупреждение с суммой. В профиле клиента отрицательный баланс показывать как «Задолженность: X ₽» |
| 1.5 **Напоминания о просрочке** | Ежедневная сводка менеджеру в Telegram: активные overdue-аренды + должники (после 0.2) |

### Этап 2 — Частичный возврат и добор позиций (1–1,5 недели) — ядро цепочки

| Задача | Что делать |
|--------|-----------|
| 2.1 **Контракт возврата по позициям** | `RentalReturnRequest` → опционально `items: [{equipment_id, accessory_ids_returned, confirmed}]`; отсутствие поля = «возвращается всё» (обратная совместимость). Ответ — пересчитанные credit/surcharge и итоговый состав |
| 2.2 **Логика частичного возврата** | Возврат части = аренда продолжается с оставшимся составом: убрать позиции из `rental_equipment`, пересчитать `total_cost` через `FinancialService.calculate_final_price` по оставшемуся составу за [start, end], разницу зачислить новой операцией `PARTIAL_RETURN_CREDIT` (день за день сокращения + ставка позиции). При возврате последней позиции — completed + `actual_return_date` (текущий путь). Промокод: пересчитать по той же логике, что продление (перевалидация, дельта) |
| 2.3 **Добор позиций** | `AdminRentalUpdate.equipment_ids_add` или `POST /rentals/{id}/items`: `validate_equipment_availability` на [start, end] (advisory-локи уже есть), добавить в состав, дельта-списание по образцу продления (`rental_update_service._apply_price_recalculation`) |
| 2.4 **Порча/недостача** | При возврате (полном/частичном) опция `damage_fee` (сумма назначает менеджер, комментарий обязателен) → новая операция `DAMAGE_FEE_DEBIT` в баланс |
| 2.5 **Фронт** | `ReturnRentalDialog`: чекбоксы по позициям (все выбраны по умолчанию), предпросмотр кредита/доплаты до подтверждения (через /calculate), обязательный ConfirmationDialog с итоговой суммой. `EditableRentalCard`: «Добавить оборудование» с мини-каталогом и проверкой доступности на срок аренды |
| 2.6 **Тесты** | Юнит: математика частичного возврата (кредит по позициям и дням, потолок, промокод), добор (анти-овербукинг, дельта, доступность), возврат последней позиции, damage_fee. Интеграционные на реальной сессии. e2e-шаг: возврат 1 из 2 позиций |

### Этап 3 — История отмен вместо удаления (2–3 дня)

|--------|-----------|
| 3.1 **Статус cancelled** | `cancel_*_reservation` и удаление аренды → `status=cancelled` + `cancelled_at`, `cancelled_by_id` (миграция). Списки: по умолчанию скрывать отменённые, в админке — фильтр «Отменённые». | 3.2 **Дашборд** | Счётчики отмен за период (резервы/аренды) |
| 3.3 **Окно отмены** | Перевести «день создания» с UTC на Europe/Astrakhan (`business_today`), устранить укороченное утреннее окно |
